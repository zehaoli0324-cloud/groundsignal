# 使用方案：一次公司研究如何形成可审查结果

先完成 [部署方案](18-deployment-guide.md)。以下命令在仓库根目录、已安装依赖的 Python 环境中执行。所有 `--out` 使用新的或空目录；示例编号重复时改为下一编号。无依据的字段留空，缺结果写缺口，不能补成确定关系。

## 一次研究应交付什么

交付三类材料：原文与运行清单、逐条待审关系、带证据和缺口的研究摘要。不要把搜索命中列表当公司画像，也不要把模型产物直接写入已确认关系图。

| 角色 | 负责内容 | 不应独自完成的判断 |
|---|---|---|
| 研究员 / 采集执行者 | 目标、来源、计划、采集、初审、缺口 | 不能凭搜索排名判定可靠性 |
| 复审者 | 高风险关系、来源独立性、商业阶段、反证 | 不用“另一个模型也这么说”替代证据 |
| 运维 / 数据负责人 | 密钥、额度、权限、保留与删除 | 不替代研究事实审核 |

一个人可兼任，但实控、重大股权、排他供应等关键结论进入正式报告前应由另一位人类复审。以下门槛是项目建议，尚未由程序强制执行。

## 步骤 1：写研究问题与边界

**用途：** 让“搜某公司”变为能回答的问题，防止结果越多越偏。

复制 `docs/templates/research-review.md` 到本次运行目录，写明：公司法定主体、研究日期、产业环节、重点产品、时间范围、最终用途、允许的来源和搜索预算。例如：“核对公司 A 近 12 个月公开披露的先进封装合作方；区分送样、认证、订单、交付；查找终止或否认信息。”

**产物与成功判据：** 研究记录中有明确问题，九个维度可逐项写“本轮需要 / 不需要及原因”。竞争关系必须限定产品与市场；母公司与子公司分别标识。

**失败处理：** 主体不清先做身份核验；问题太大先分成多次运行，不靠提高文档上限一次解决。

## 步骤 2：编辑目标、审阅计划

**用途：** 控制实际检索词、时间提示和一手入口，发现系统将搜索什么。

```bash
python scripts/research.py prepare --target research-runs/setup-01/target.json --intensity standard --models none --providers brave tavily --out research-runs/research-02
```

打开生成的 `target.json / config.json / plan-preview.json`。standard 为每个已选维度生成中文、英文和官网三种角度；九维时共 27 条。别名要真实且无同名歧义；没有可靠英文名不强造。来源条款不允许一般自动抓取时，改为只采集已批准种子，见部署步骤 5。

**产物与成功判据：** 所有预期维度有任务；关键词没有把股东混成客户；预算符合额度。搜索日期只是提示，各服务支持可能不同，仍要审核原文日期。

**失败处理：** `unplanned_dimensions` 非空先调整范围或查询预算。DeepSeek 搜索单条超过 128 字符会被明确拒绝；优先缩短准确别名或拆分问题，不截掉关键主体。并非所有布尔 / site / 时间语法都被提供商等价执行，结果要抽查。

## 步骤 3：先采集，再做技术审计

**用途：** 先确定有没有合法可用的原文，把服务故障与行业信息缺失区分开。

```bash
python scripts/research.py doctor --config research-runs/research-02/config.json --target research-runs/research-02/target.json
python scripts/research.py run --target research-runs/research-02/target.json --config research-runs/research-02/config.json --out research-runs/capture-02
python scripts/research.py audit --run research-runs/capture-02/run.json --out research-runs/audit-02
```

**产物与成功判据：** 先看 `search_statuses`，再看 `document_statuses`，最后看九维覆盖和预算诊断。至少打开一份 HTML / PDF 原文，对照公司、日期、标题、正文及页码。抓到网页但正文无关也不算有效证据。

**失败处理：** `NO_RESULTS` 是该查询没结果；`NOT_CONFIGURED` 是没配服务；429 / timeout 是未完成。九维都发过查询不等于九维都有事实证据。`dimensions_without_fetched_evidence` 只反映检索来源关联，不能证明该维度被完整研究。

## 步骤 4：按缺口补搜，而不是盲目加量

**用途：** 把后续预算投给尚未回答的具体问题。

在研究记录登记“维度—缺什么—下一证据—停止条件”。例如：“供应关系只有新闻转载，缺客户或供应商原公告；下一步找公告、年报、采购结果；找不到时保留为线索”。把找到且允许抓取的一手 URL 放入下一份目标的 `seed_urls`，另起目录运行。

**产物与成功判据：** 补搜新增独立原始材料，或明确说明仍不可得。每一轮都能解释为何继续、为何停止；对方名称不明确时不自动创建新公司。

**失败处理：** 只有相同通稿转载时，记录同源，不把几十家网站算成几十次确认。没有披露客户名单只能说“未找到公开披露”，不能推断没有客户。多跳扩展的边数和边界见 [挖掘方案](20-search-mining-strategy.md)。

## 步骤 5：在已批准正文上抽取候选

**用途：** 用小模型节省重复阅读时间，用大模型处理困难候选，同时保持输入可追踪。

完成部署中的模型设置及云端处理准入后：

```bash
python scripts/research.py extract --run research-runs/capture-02/run.json --config research-runs/model-session-01/config.json --out research-runs/extract-02
python scripts/research.py validate --run research-runs/extract-02/run.json
python scripts/research.py audit --run research-runs/extract-02/run.json --out research-runs/extract-audit-02
```

这里刻意复用一个 quick 模型配置，因此抽取仍受其 8 次总模型 / 3 次大模型调用限制；如果正文较多，先评估并提高配置预算，不能把未处理文档当“没有关系”。`extract` 不重新搜索，不下载页面，也不会更新首次发现时间。

**产物与成功判据：** `review-queue.json` 中有候选或清楚的空结果 / 失败记录；attempt 是真实 `OK` 而非 `SIMULATED`；大模型升级没有因缺钥匙或额度被跳过。程序会检查引文、字段和部分阶段错误，所有候选依然待审。

**失败处理：** 模型不可用先解决服务和实际模型名。被拒输出要回看原文与提示词，不放宽引文约束以追求条数。长文件只选择有限正文片段，并非全文分块深读；重要表格和脚注需人工补查。

## 步骤 6：逐条做实体与关系审核

**用途：** 防止“有引文”被误当成“含义正确”。审核单位是有明确边界的主张，不是整篇文章。

在模板的候选裁决表记录 candidate_id、document_id、主体与客体法人 ID、关系方向、产品、阶段、极性、事件时间、原文页码 / 区间、上下文、独立来源组、结论和审核人。必须回到完整原文，而非只读截取引文。

| 原文情形 | 可以记录 | 不能升级为 |
|---|---|---|
| A 为 B 送样，正在测试 | A → SUPPLIES → B；SAMPLE / TESTING；按上下文限定 | 已量产、长期大客户 |
| A 持有 B 少数股权 | A → OWNS → B；比例另记原文及时间 | 实际控制、全资子公司 |
| A 与 B 做同类产品 | PRODUCT_OVERLAP，限定具体产品和市场 | 直接竞争已被证实 |
| A 否认供应 B | 原否认主张及 NEGATED、声明主体、日期 | 既往从无合作、未来必不合作 |
| 匿名“头部客户” | 保留匿名线索及信息缺口 | 根据猜测补成某家知名公司 |
| 合作备忘录、联合实验室 | 有限定的 PARTNERS_WITH、PLANNED 等 | 采购金额、排他供货或商业收入 |

**产物与成功判据：** 每条主张能让复审者用相同原文独立核对。持股比例、交易金额、币种、有效期、产能口径目前没有完整结构化候选字段，先在审核记录明确保存，不假装数据库已支持。

**失败处理：** 同名、翻译名、主体链不清就保留 UNCONFIRMED；需要跨段推理且当前精确引文规则不支持时，留人工记录，不能伪造一段拼接引文。

## 步骤 7：复审高风险主张，并保留分歧

**用途：** 避免一次误判污染供应链图、投资图和关键人物关系。

所有权 / 实控、重大订单、独家供应、竞争认定、否定传闻由人类复审；优先查监管文件、交易双方披露和终止 / 更正。两个模型相同不是两个独立来源，来自同一通稿的多个域名也不是独立来源。

**产物与成功判据：** 高风险记录有另一位复审者及证据；相互冲突的材料同时保留，注明各自事件时间、有效范围及未解决问题。若只能由一人处理，正式输出明确写“未双人复审”。

**失败处理：** 争议无法消除则标记争议，不强选最大模型答案。人工审核记录目前没有自动写回逐条候选状态的命令，不手改 `run.json` 中的 PENDING 或指纹制造通过。

## 步骤 8：查看账本交接与形成研究摘要

**用途：** 让读者查看来源轨迹，同时把已审主张、线索和缺口说清楚。

```bash
python scripts/evidence_demo.py report --input research-runs/extract-02/ledger/manifest.json --out research-runs/extract-02/ledger.html
python scripts/evidence_demo.py review --help
```

`ledger.html` 可本地打开。当前交接是一篇原文一个 `UNCLASSIFIED_LEAD`，来源 UNKNOWN、原始来源尚未审核，候选 ID 只在 lineage 中。已有 `review` 命令针对 evidence 添加审核，**不是逐条候选发布命令**；`CONFIRM` 要求 T1 与 `original_source_checked=true`，本管线交接不满足，不能靠加一条 review 自动完成来源晋级。来源核验、实体归一、逐条关系入图的正式写入流程仍待实现。

先把人工研究摘要写在本地审核记录中：结论、适用时间、短引文与链接、阶段、审核状态、冲突、缺口。对外分享前按来源许可与个人信息最小化检查，只共享获准内容；不要把含全文的 `run.json`、`ledger.html`、sources 目录默认公开。

**产物与成功判据：** 摘要中的每一句关键结论有原文与审核 ID；不会把全部待审队列包装成已确认公司网络。

**失败处理：** 缺少逐条发布功能时继续保留待审状态；不要通过改 Schema 或直接编辑旧知识库把功能缺口掩盖掉。

## 步骤 9：比较模型并决定是否扩大使用

**用途：** 在相同原文上比较质量与成本，避免用榜单替代项目验证。

```bash
python scripts/research.py compare --run research-runs/capture-02/run.json --config research-runs/model-session-01/config.json --out research-runs/compare-02
```

一个 compare 会运行 small_only、large_only、cascade 三组，每组都有独立预算，总调用上限可达单组的三倍。没有人工标签时精度为 `UNASSESSED`；不应宣称哪套胜出。需要金标时按 `examples/search/synthetic-gold.json` 的结构制作真实标注，将 synthetic 改为 false 并使用真实文档 ID、文本 SHA 与人工主张，再通过 `--gold` 输入；不要把合成答案当真实评测。

**产物与成功判据：** 先用 5 家公司、100–200 条真实主张建立初始样本；按公司 / 文档切开开发集和留出集，避免转载同时落入两组。分别比较字段精确率、漏报、严重错误、升级率、时延和账单，再选模型。小样本结果要连同样本数披露。

**失败处理：** 留出集错误过多，先修来源、实体或抽取环节；不能只加模型规模。模型、prompt、解析器、配置变化后重新评测相关样本。未配置真实账单价格时金额保持未知。

## 步骤 10：复查、保管与结束研究

**用途：** 防止旧股权、旧订单、旧产能被继续当作当前事实，并控制数据保留成本。

按主张类型人工设置下次复查日期：订单 / 量产 7–30 天，股权 / 实控 30–90 天，基础身份 90–180 天，重大更正立即复查。这是起始建议，需随使用场景调整；当前账本的全局陈旧判断与逐关系策略不同，未自动实现这些周期。

**产物与成功判据：** 保留旧证据、记录新证据和变更原因；到期删除 / 归档按来源与个人信息保留策略执行，覆盖缓存、备份、导出和供应商副本。运行目录与审核表一起受控备份，记录代码 SHA、配置和模型实际返回版本。

**失败处理：** 无法证实仍有效就标记过期 / 待复查；复制旧文件或重跑 extract 不会产生新的来源新鲜度。当前不提供自动定时监控或全副本删除工具，需由负责人安排并留记录。
