# 数据搜索与挖掘力度方案

目标是找到足以支持判断的证据，并明确还缺什么。搜索量、独立证据量、关系强度、事实可靠性应分别衡量。单纯加查询、加 agent 或换最大模型不会自动解决主体错误和来源同质化。

## 搜索的六个阶段

| 步骤 | 用途 | 怎么做 | 完成标志 / 停止条件 |
|---|---|---|---|
| 1. 核对主体 | 避免同名、品牌、母子公司混淆 | 名称、别名、法定名称、官网、注册地 / 证券代码交叉核对，记录依据 | 主体清楚后再扩展；不清楚时停止建关系 |
| 2. 找权威入口 | 弥补搜索排名遗漏 | 官网公告、IR、监管披露、年报、招股书、采购公告；核对来源许可后放入 seeds | 找到原件及日期；许可不明的全文暂不采集 |
| 3. 多角度搜索 | 提升语言、来源、时间覆盖 | 用六轮查询策略，保存命中来源、查询和首次观察时间 | 有有效正文或明确技术失败 / 缺口 |
| 4. 挖具体关系 | 从“提到公司”推进到可审核事实 | 找对方名称、产品、合同 / 股权、阶段、事件时间、反证 | 得到原子主张或记录证据不足 |
| 5. 反向与反证核对 | 发现营销措辞、旧事实和单边叙述 | 对方公告、历史版本、更正、否认、终止、非独家、剥离 | 形成独立证据链；冲突保留，不强行合并 |
| 6. 收束并复查 | 控制成本，避免无边界抓取 | 审核新增独立材料、未解决问题和剩余预算 | 达到证据目标、预算、低边际收益或合规停止线即停 |

阶段 1、2、4、5、6 仍需研究员决策。当前程序支持有界查询、采集、抽取和缺口报告，尚未实现自动实体归一、对方反向追踪或图上的递归挖掘。

## 三档运行强度：程序实际会做多少

用 `prepare --intensity` 生成以下配置。数字都是每次运行的上限，预算、失败、缓存、模型关闭和总时长可能使实际执行更少。

| 上限 / 行为 | quick | standard | deep |
|---|---:|---:|---:|
| 九维情况下的计划查询数 | 9 | 27 | 54 |
| 搜索 API 实际调用 | 9 | 54 | 108 |
| 每查询每提供商最多结果 | 3 | 4 | 5 |
| 最多尝试正文文档 | 5 | 15 | 30 |
| 抓取调用 | 24 | 64 | 128 |
| 模型总调用（含大模型） | 8 | 24 | 48 |
| 大模型调用（总调用的子集） | 3 | 9 | 18 |
| 总时长边界检查（秒） | 300 | 900 | 1800 |
| 查询角度 | 中文发现 | 再加英文、官网 | 再加披露文件、商业阶段、反证 |
| 建议场景 | 新目标试采、验证服务 | 一家公司常规研究 | 已有具体缺口的定向补充 |

基础配置的输入上限仍为 12,000 字符、输出 2,048 token、单文档下载 8,000,000 bytes、单请求超时 20 秒，间隔 1 秒、搜索缓存 6 小时；`prepare` 不自动改变这些字段。应按文件与服务限制再调整。字符不是 token，不能直接换算费用；12,000 字符不代表读完一份年报。

**实际执行顺序：** 每轮先覆盖各已选维度，再进入下一轮；提供商按配置顺序依次执行整个计划。54 条计划、108 次搜索预算在无失败 / 缓存等情况下可以覆盖两家提供商；若配置三家，第三家可能没有额度。quick 通常只够第一家完成一轮。要公平比较提供商，用同一查询集、每家独立运行和预算，不能拿最后一家额度不足的结果作对照。

**重要边界：** deep 仅增加六种查询角度和预算，不会自动读取命中页面的所有链接、探索二跳公司或全文分块抽取。只有三维时六轮最多 18 条，不会为凑够 54 重复搜索。基础 `config/search.default.json` 保留较小试验预算；三档以 `prepare` 生成值为准。

## 每一轮查询的用处

| 轮次 | 实际 purpose | 查询角度与用途 | 局限 |
|---|---|---|---|
| 1 | discovery_zh | 中文名 + 该维度词；先发现行业表述与常用别名 | 容易命中营销与转载 |
| 2 | discovery_en | 最短的真实 ASCII 别名 + 英文维度词；覆盖英文披露 | 别名歧义需审核；无英文名就用原名 |
| 3 | official_followup | 首个官网域名限定；没有域名时提示“官方公告 原文” | 首个域名不是全部官方渠道，其他渠道用 seeds 补 |
| 4 | filing_followup | 年报 / 招股书，cninfo 与 SEC 域名提示 | 不是全球监管库全覆盖；不同引擎语法可能不同 |
| 5 | commercial_stage | 合同、金额、试产、量产、认证、供货；找实际进展 | 关键词出现不代表已达到该阶段 |
| 6 | countercheck | 否认、终止、历史、更正、非独家；找限制与反证 | 没搜到反证不是事实成立的证明 |

程序不会静默截断超过提供商限制的长查询；DeepSeek 的 128 字符限制仍单独校验。监管地区、语言、专业词可在下一轮目标或将来的专门查询配置中细化；当前没有任意自定义 query 文件入口。

## 九维信息应挖到什么程度

| 维度 | 优先问题 | 一手材料与核对重点 | 易误判处 |
|---|---|---|---|
| 上游 | 谁给目标供应什么，当前处于什么阶段？ | 供应商 / 目标披露、采购、认证、产线说明；按材料、设备、制造、封装分类 | 产业链相邻 ≠ 实际供货 |
| 下游 | 谁买了什么，交付还是测试？ | 客户公告、采购中标、财报；产品、交付期、金额口径 | 中标、试用、渠道库存 ≠ 已确认收入 |
| 同类 / 竞争 | 哪个产品、地域、客户群有重叠？ | 产品手册、招股书竞争章节、双方公开定位 | 同行业 ≠ 直接竞争；不能把分析推断混成披露事实 |
| 投资方 | 谁在何时以何种方式投资目标？ | 融资双方、监管披露；直接 / 间接持股、轮次、比例 | 基金管理人 ≠ 出资人；历史投资 ≠ 当前股东 |
| 被投资方 | 目标投了谁，有没有控制权？ | 对外投资、子公司附注、并购与剥离公告 | 少数投资 ≠ 控制；控制 ≠ 全资 |
| 关键人物 | 创始、现任管理、受益所有权分别是谁？ | 公司与监管公开文件；任期、层级、法人关系 | 创始人 ≠ 现任 CEO ≠ 实控人；避免无关个人信息 |
| 产品 | 型号、代际、技术路线、认证、供货如何？ | 官方产品说明、客户资格验证、披露；分清状态 | 发布 ≠ 可买；送样 ≠ 量产 |
| 产能 | 在哪里、何种口径、规划还是投产？ | 环评 / 项目公告、财报、投产公告 | 设计产能 ≠ 有效产能；规划投资 ≠ 已投入 |
| 反证 | 有无否认、更正、撤单、延期、剥离？ | 双方公告、监管问询及回复、历史版本 | 否认措辞的对象与时间必须精确 |

注册表 `config/search.sources.json` 的 T1/T2/T3 只是来源提示；不会让一条关系自动获得相同可靠性。即使年报是原件，也可能描述历史情况、风险假设或不具名客户。

## “只收集密切合作方吗”：先分开两个轴

建议收集有合理证据的候选，默认视图优先展示**当前、重要、已审核**的关系，历史、弱关系、匿名线索仍单独保留。可靠性与商业密切度不能互相替代。

| 轴 | 人工判断依据 | 允许的未知状态 |
|---|---|---|
| 证据可靠性 | 原件真实性、原文是否支持、主体 / 时间匹配、独立来源、反证 | 待核实 / 争议 / 过期 |
| 商业密切度 | 交易占比、金额、重复合作、独家性、产品绑定、合作持续期 | 披露不足，无法判断 |

例如，官网合作备忘录可证明“宣布合作”，仍不能证明交易紧密；一份持续采购合同可以很重要，但没有核对真实性前仍不可靠。没有披露采购占比时，不用报道次数、模型自信分或官网 logo 推算密切度。这两个轴当前没有完整编码入候选 Schema，先记人工表，后续再加模型和 UI。

## 多跳挖掘的受控方案

当前版本手动执行以下过程，下一阶段才做 agent 工具编排：

1. **固定中心公司与九维问题。** 用途：避免扩成整个半导体互联网。产物：中心目标与预算。
2. **从原文提出一跳候选。** 用途：只沿可定位证据扩展。每维先选至多 5 家有名称、有来源的候选；匿名和同名未解者不扩展。
3. **人工归一并审核扩展价值。** 用途：避免同一公司重复与弱关系爆炸。记录主体 ID、产品、时间、缺口与下一问题。
4. **对获准候选建立独立目标 / 运行。** 用途：从对方披露反查该边。种子 URL、查询与父运行 ID 记入人工记录；当前 prepare 不会自动继承这条 lineage。
5. **限制二跳。** 用途：只追重大缺口，比如母公司是否控制实际供应商；每轮最多 10 个新实体，最多二跳，全部共享研究总预算。这是人工策略，CLI 不会合并各次运行的额度。
6. **收束与记录没找到的部分。** 用途：把“尽调深度”变成可说明的覆盖范围；给出下一次需要的证据，不无限重试。

停止任一分支的条件：授权不允许或有疑问、触及验证码 / 登录付费边界、主体未解、预算或时限到达、连续两轮没有新增独立原始材料、已回答问题且反证检查完成。连续两轮无新增是建议的人工停止规则，尚无自动收敛判定。

## 工具、小模型、大模型与 skill 如何分工

| 层 | 采用方式 | 用处 | 目前落地状态 |
|---|---|---|---|
| 固定代码 | 搜索 API、HTTP、pypdf、Schema、指纹、预算 | 重复工作可测试、失败明确、成本有界 | 已有；API / 真实网站仍需部署环境验证 |
| 可选爬取 / 解析器 | Crawl4AI 处理许可范围内动态页；Docling 试验复杂文档 | 补静态抓取不足 | 接口已有，重型依赖未实测；Docling 页码不可据此保证 |
| 本地小模型 | Qwen 9B 起步，对照 4B | 简单字段与候选抽取，不直接发起工具调用 | 配置已有，未实跑权重 |
| 大模型 | DeepSeek Flash / Pro 复核高风险、失败、分歧与抽样 | 集中处理困难语义 | 路由已有，真实质量未知 |
| 研究 SOP / skill | 固定证据要求、关系方向、失败样本与审核清单 | 让 agent 每次按同一方法研究 | 本仓库现为 prompt + Schema + 手册；不是已安装的通用自动研究 skill |
| 规划 agent | 提议缺口、下一查询 / 来源，由有界工具执行 | 将人工循环逐步自动化 | 待做；不得绕开来源门禁、预算与审核 |

不因项目热度把通用浏览器 agent 接成无限权限爬虫。选型先看维护与许可证、可保存原文、稳定 ID、预算 / 重试 / 限流、可观察日志、受限工具、测试与中文 PDF 表现，再测本项目留出集。已有候选比较与一手链接见 [proposal](15-search-evidence-proposal.md)；本文没有新增“最新最强”性能结论。

## 怎样衡量“挖得够深”

每轮分别记录：计划 / 执行查询数、技术失败、各维有效正文、原始来源组数、已人工审查主张数、高风险复审率、当前 / 历史比例、关键问题未解数、新增独立材料数、实际账单和人工时间。

程序 audit 目前只计算技术状态、文档与候选计数、预算诊断和按查询关联的维度覆盖；原始来源组、事实正确率、关系重要性、有效性、人工成本都需要人工记录。**不得把命中条数、多个域名或合同 / 股权关键词出现次数当作事实质量分。**
